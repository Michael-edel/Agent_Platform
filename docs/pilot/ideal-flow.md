# Ideal End-to-End Flow (история)

## История (пошагово)

1) **Бухгалтер получает счёт по почте** (PDF от поставщика).

2) **Бухгалтер загружает PDF в систему** (одна команда / один запрос, без UI в пилоте).

3) **Система сохраняет документ**:
- присваивает документу идентификатор (DocumentId / ArtifactId),
- фиксирует tenant,
- делает документ доступным для просмотра через API.

4) **Система создаёт PaymentId** (корреляционный якорь):
- создаётся запись платёжного поручения,
- сохраняются ключевые поля: сумма, валюта, назначение, получатель,
- сохраняются ссылки: tenant_id, document_id и (если есть) case_id.

Важно: **даже если интеграция/экспорт временно недоступны — PaymentId уже есть** и не пропадает.

5) **Бухгалтер отправляет платёж на согласование**:
- статус платёжного поручения меняется на “ожидает согласования” (или сразу “approved” при auto-approve политике),
- система фиксирует событие “payment submitted”.

6) **Директор получает запрос на согласование**:
- директор выполняет действие `Approve` или `Reject`,
- система фиксирует кто, когда и с каким комментарием принял решение.

7) **Платёж уходит дальше**:
- экспорт/интеграция (1С / банк / CSV) выполняются отдельным шагом,
- если экспорт недоступен: это фиксируется как ошибка/событие, но **PaymentId остаётся валидным**.

## Что видно в любой момент (аудит/трассировка)

- **Какой документ** был источником (DocumentId / ArtifactId).
- **Какой платёж** создан (PaymentId).
- **Кто и когда** отправил на согласование.
- **Кто и когда** одобрил/отклонил, с комментарием.
- **Что произошло с экспортом/интеграцией** (успех/сбой и причина).
