# Demo Script v1 (15–20 минут) — Денежный контур end-to-end

## Цель демо

Показать полный цикл: **Документ → 1С → Платёжка → Согласование → Экспорт → Выписка → Сверка → Закрытие кейса**. Фокус: управляемость, audit trail, наблюдаемость, поведение при исключениях.

## Подготовка (до звонка)

- 1 tenant для демо: `tenant-demo` (или [placeholder]).
- Тестовый набор:
  - 1 входной документ (счёт/инвойс) с ожидаемыми полями
  - 1 тестовая “платёжка” на согласование
  - 1 выписка (CSV) с транзакцией для сверки
- Доступы:
  - UI (если используется) или API (curl/postman)
  - Grafana/Prometheus (dashboard “Billing SLA / Invoices v2”)

## Сценарий по шагам (что сказать / что показать)

### 1) Документ → артефакт (2–3 мин)

**Что сказать**
- “Стартуем с документа. Все изменения статусов фиксируются в audit trail, чтобы всегда было понятно кто/что/когда.”

**Что показать**
- Создание/появление артефакта документа (UI или API).
- Логика статусов и связанный кейс (если создаётся при исключении).

### 2) Артефакт → 1С job (2–3 мин)

**Что сказать**
- “Интеграция 1С идемпотентна: повторный запуск не создаёт дубликатов. Ошибки диагностируемы по кодам.”

**Что показать**
- Появление integration job (pending → succeeded/failed).
- Где смотреть ошибки и retry policy (коротко, без деталей реализации).

### 3) Платёжное поручение (2–3 мин)

**Что сказать**
- “Из данных формируется платёжное поручение. Дальше оно проходит согласование по ролям.”

**Что показать**
- Создание payment order.
- Поля, которые важны казначею (контрагент, сумма, назначение, дата).

### 4) Согласование (2–3 мин)

**Что сказать**
- “Согласование — управляемый процесс: кто должен утвердить и что происходит при задержках.”

**Что показать**
- Шаги approval, смена статуса.
- Что происходит при “застрявшем” approval (кейсы/задачи, если включено).

### 5) Экспорт (1–2 мин)

**Что сказать**
- “Экспорт выполняется только после нужных статусов; повторяемость важнее скорости.”

**Что показать**
- Экспорт в согласованный формат (CSV/1С).
- Где появляется артефакт экспорта (путь/идентификатор).

### 6) Выписка (2–3 мин)

**Что сказать**
- “Импорт выписки — точка правды для закрытия платежа. Здесь важна прозрачность сопоставления.”

**Что показать**
- Импорт выписки и список транзакций.
- Выделение транзакции “нашего” платежа.

### 7) Сверка (auto-match / manual match) (2–3 мин)

**Что сказать**
- “Сначала auto-match. Если confidence недостаточен — ручной match, но с audit trail.”

**Что показать**
- Автоматическое сопоставление (matched=true) или ручной match (оператором).
- Событие сверки в истории.

### 8) Закрытие кейса (1–2 мин)

**Что сказать**
- “Кейс закрывается, когда контур завершён. Это важно для операционного контроля.”

**Что показать**
- Закрытие кейса/задачи, итоговый статус.

## Что показать в Observability (по ходу или в конце, 2–3 мин)

- Dashboard “Billing SLA / Invoices v2”:
  - funnel/статусы
  - time-to-paid p95 (по provider)
  - SLO секция (ratio/burn rate), если включена
- Top errors / failure reasons:
  - `topk(10, sum(rate(billing_jobs_failure_reasons_total[15m])) by (provider, error_code))`

## 3 типовых вопроса клиента и ответы (RU)

**1) “Как вы гарантируете отсутствие дублей (платежей/джобов)?”**  
Ключевой принцип — идемпотентность: события и операции имеют idempotency keys, повторная обработка безопасна. При частичном успехе система делает reconcile/refresh вместо повторного создания.

**2) “Что происходит при сбое 1С/банка/вебхуков?”**  
Система переходит в degraded mode: фиксирует диагностируемую ошибку, не делает опасных повторов, ставит задачи (кейсы), и восстанавливается через retry/backoff или ручной операционный шаг. Наблюдаемость позволяет быстро локализовать проблему.

**3) “Где граница ответственности (ваша vs наша)?”**  
Мы отвечаем за корректную работу платформы и интеграционного контура в согласованной конфигурации; клиент обеспечивает доступы, данные и бизнес-правила (кто согласует, какие форматы, какие поля обязательны). В пилоте это фиксируется в чеклисте и weekly review.
